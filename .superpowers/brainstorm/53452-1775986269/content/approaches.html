Carousel Card Redesign: Approaches

Static height, image-driven width — three ways to structure it

A

Minimal Change — Update existing components in place

Modify GameCard and each shelf component directly. Change card sizing from fixed-width to fixed-height. Each shelf keeps its own scroll logic.

Pros

  • Smallest diff, least risk
  • No new components to maintain

Cons

  • Scroll logic stays duplicated across 13+ shelf components
  • No Design→Content→Role hierarchy for carousels
  • Harder to change carousel behavior later
B

Recommended — Extract shared ScrollShelf + CarouselGameCard

Create a shared Design layer ScrollShelf (scroll container, arrows, scroll state) and a Content layer CarouselGameCard (fixed-height card with image-driven width). Existing shelves become thin Role wrappers.

Pros

  • Follows Design→Content→Role hierarchy
  • Eliminates duplicated scroll logic (13+ copies → 1)
  • Centralized height constant — easy to tweak
  • Matches the player app's component structure

Cons

  • Larger diff — touches many shelf files
  • More up-front work
C

Full Redesign — New carousel system with virtualization

Build a new carousel system with windowed rendering (only render visible cards), intersection observer-based lazy loading, and full keyboard/gamepad navigation.

Pros

  • Best performance for large lists
  • Gamepad-ready like the player app

Cons

  • Way more complexity than needed
  • Variable-width cards make virtualization harder
  • YAGNI — current shelves have ≤20 items
